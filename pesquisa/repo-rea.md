## 2. Capability map (README table "What you can analyze"; docs/index.md)
REA = MCP server + CLI ("one CLI and MCP server"), ~172 tools (docs/client-configuration.md), returns "Evidence" records with explicit unknowns/limitations. Host: Node 22.19+/24.11+/26+; Linux/macOS primary, Windows x64 "experimental" Ghidra P0 (docs/windows-ghidra-p0.md).
- Native ELF/PE/Mach-O: needs Hopper, Ghidra (12.1.x, verified 12.1.4, JDK 21+) or IDA (via MCP bridge ida-free-mcp / idalib supervisor; docs/ida-provider.md, "experimental profile", direct callers unavailable). Output: pseudocode, assembly, xrefs, call graphs, types, p-code dossiers (docs/native-investigation.md, ghidra-provider.md). Windows PE EXE/DLL (x86/x86-64, native only), DOS MZ/COM (docs/ghidra-dos.md, 16-bit real mode), raw binaries (raw-binary.md), MIPS/PSP/RISC-V pages, Go build metadata (built-in), ELF layout via pwntools (Linux x64). Windows P0 is read-only (no annotations). Pseudocode "is not original source"; Hopper vs Ghidra text never compared as equal.
- .NET/managed: built-in static PE/CLI parser, no external engine (docs/managed-code-analysis.md): metadata, CIL, member comparison across builds, P/Invoke boundary checks, BYO decompiler import (ILSpy `ilspycmd` via REA_ILSPY_CMD_PATH, `import_managed_reconstruction`, labelled "non-canonical inference"). Does NOT unpack single-file hosts, decode IL2CPP, or map native bodies for C++/CLI, R2R, NativeAOT. NativeAOT: read-only parser only for x64 PE32+/.NET 8 RTR 9.1 (docs/ghidra-nativeaot.md); optional locally built Ghidra JAR (Linux).
- Java/Android: APK static analysis via headless JADX = third-party jadx-headless-mcp 0.7.1 JAR (REA_JADX_MCP_JAR) + full JDK 17+ (docs/android-analysis.md); resources via Apktool>=2.7.0 (REA_APKTOOL_COMMAND); engine-grade decompile via caller-started JEB 5.48 MCP server (REA_JEB_MCP_URL, docs/jeb-analysis.md; headless instances do not advertise open_project); ADB device inspection/acquisition (adb-device-analysis.md); Flutter/Dart AOT triage (flutter-analysis.md). Desktop Java (.jar/.class, Swing) is NOT documented anywhere (grep found nothing).
- Electron/JS: built-in static analysis, no engine (javascript-artifact-reconstruction.md, javascript-application-graph.md): modules, imports, source maps, IPC, routes, native add-ons, ASAR; runtime observation via V8 inspector/Electron CDP (javascript-runtime-observation.md, electron-observation.md); Frida (frida-instrumentation.md).
- Web bundles/browser: attach-only CDP to a user-run Chrome-family browser; Playwright providers for owned scenarios; HAR/mitmdump capture analysis; Wakaru for source recovery (see section 4).
- Firmware: Binwalk 3.1.x inspect + Unblob 26.6.x extract, Linux x64 only, needs util-linux prlimit; arbitrary firmware bytes are not native-admitted, select an extracted ELF for Ghidra (firmware-analysis.md).
- EVM: offline interface inference with bundled EVMole 0.9.3, flat legacy bytecode only, EOF containers unsupported (evm-bytecode.md). Also WASM (WABT 1.0.42), SQLite (Node 24.15+), packets (TShark), signals (sigrok), recorded crashes.
- iOS/Apple: Hopper/Ghidra for Mach-O; execution-free inventory projection of IPA/.app/DMG with path-based framework hints (RN, Flutter, Unity); plist/keyed archive/asset catalog/Interface Builder inspection tools; Swift type analysis/demangling; ObjC class tools. No plist/CMS semantics in the projection; hints are not observed loading (apple-application-analysis.md). Harmony (harmony-analysis.md) also present.

## 3. Legacy business software modernization
- Grep for Delphi, VB6, Visual Basic, PowerBuilder, FoxPro, COBOL, Clipper, Swing across README/docs/AGENTS/DISCLAIMER: ZERO hits. None is named as supported or unsupported. Nearest: Ghidra PE x86 (generic) with REA_GHIDRA_LANGUAGE_ID/COMPILER_SPEC_ID override example "x86:LE:32:default" + "borlandcpp" for "Borland C++ PE images" (docs/installation.md ~L640); Ghidra DOS 16-bit MZ analysis (Clipper/DOS-era apps conceptually); TH04 PC-98 DOS showcase (README). No Delphi RTTI/DFM/VCL form recovery, no VB6 P-code/native handling, no PowerBuilder PBD, FoxPro/Clipper formats, no COBOL, no database/SQL schema extraction from client apps (only SQLite file inspection). Expect plain Ghidra/IDA-quality decompilation of Delphi/VB6 native code, no language-aware help. .NET Framework assemblies are the best-covered legacy case (CIL inspection + BYO ILSpy import). Java Swing: unsupported/undocumented.
- Also "NativeAOT" is the only matched compiler-specific term.
- "Reconstruction" as documented is NOT automatic source regeneration. REA never emits a rebuilt project. The workflow is analyst/agent-driven: (1) investigate with providers (pseudocode, CIL, graphs) -> Evidence; (2) the agent (LLM) writes the reimplementation (README showcases: DX-Ball sound-pan in C passing 3,205 original-x86 cases and reproducing 63 function bytes; TH04 recovered C++ compared against historical compiler output; repos by contributor N0zoM1z0); (3) REA provides the verification scaffolding:
  - `import_managed_reconstruction`: attach externally decompiled C# to exact static member identities (docs/managed-code-analysis.md).
  - `import-reference-source <dir>` (docs/cli.md ~L210): hash/index an older source tree (honours .gitignore, secret-pattern exclusion env REA_REFERENCE_SECRET_PATTERNS_JSON) for `compare_source_to_bundle`; Linux/macOS only (Windows -> unsupported_host).
  - `compare_artifacts / compare_functions / compare_process_captures` -> `verify_reconstruction` (MCP prompt in docs/mcp-prompts.md; src/contracts/promptContracts.ts L221): per-claim pass/fail/unknown for a finite spec; pass never means global equivalence.
  - `build_reconstruction_obligation_ledger` (docs/reconstruction-obligation-ledgers.md): turns Evidence into obligations (layers: cli, protocol, electron, persistence, native-abi...), each needing a unique owner (module_path/symbol/sha256), parser/schema types, fixtures for positive/negative/malformed (+cancellation) cases, and a passing verifier with comparable authority (process/runtime/packaged-process...). "A green unit test cannot close a packaged-process obligation"; static-only cannot close runtime claims; blocked/out-of-scope never counts as verified.
  - `evaluate_reconstruction_coverage`: coverage against a named replacement boundary; incomplete = partial/unknown, contradictions fail closed.
  - docs/reconstruction-readiness.md: `npm run verify:readiness` is a repo-internal conformance test of those semantics on JS CLI/Electron/native fixtures, not a public tool.
  Net: strong rigor for JS/Electron/CLI-style replacement and function-level native equivalence; for large Delphi/VB6 GUI apps you would be using it as a Ghidra/IDA wrapper plus an evidence ledger, with the "rebuild" done by you/the LLM.

## 4. Web/JS features (docs/browser-observation.md, javascript-application-workflows.md, javascript-recovery.md)
- analyze-web-bundle `<cdp_endpoint> <target_id>`: static, non-executing parse of the page's scripts: chunk edges, route/endpoint candidates (6.4: tRPC, HTTP-link, named GraphQL ops), vendor fingerprints, static WebMCP declarations, optional source-map/original-source evidence (`fetch_source_maps`: exact-origin redirect checks, no cookies/credentials/referrer, 30 s deadline, 64 MiB budget).
- discover-webmcp-tools: uses experimental CDP WebMCP domain; lists in-scope registrations with full input_schema + sha256, treated as "untrusted JSON data"; REA never exposes WebMCP.invokeTool (cannot call tools).
- compare-application-versions: compares two authenticated JavaScript Application Graph Evidence records (from analyze_javascript_application / reconcile); no file reads or code execution; unresolved items become residual unknowns.
- compare-source-to-bundle: historical source graph (from import-reference-source) vs bundle graph; scoring by source digest, source-map path, path suffix, basename; classes unchanged/modified/removed/split/merged/duplicated/unknown; static mapping only; removal needs complete inventories.
- recover-javascript-sources: Wakaru ^1.13 (verified 1.14.0), Linux x64 only, REA_WAKARU_COMMAND + prlimit; UTF-8 JS files/bundles (e.g. from export_web_scripts); never executes code.
- trace-application-feature: literal (no regex) seed (node ID, route, string, API, IPC channel, module, native export) -> full reachable subgraph, terminal paths, native handoffs; never auto-starts a provider.
- Scope rules: CDP attach-only to an already-running user browser; exact-origin scoping by default (the selected page's origin; `allowed_origins` to widen), rechecked before/after attach, `target_changed` discards mixed results; no Runtime.evaluate/navigation/input/downloads. Data minimisation: DOM text, storage values, bodies, WebSocket payloads not retained; but script sources, query strings, console text may include secrets and land in Evidence. Recommends a dedicated browser profile; "not a sandbox". Network/console coverage begins only at attach. Ethics: DISCLAIMER.md excludes bypassing auth/bot protection/access controls, copying proprietary software, circumventing DRM; "public availability ... does not by itself establish permission". Useful for a SaaS builder analysing own/authorized or interop targets; ToS compliance is left to user.

## 5. Safety / legal / telemetry / network / injection
- DISCLAIMER.md (above); SECURITY.md: private vuln reporting; "not a sandbox"; opening an untrusted binary delegates parsing to the local provider with the user's permissions; Ghidra runs in an ephemeral temp project with private home dirs, `-readOnly -deleteProject`; per-session random capability token + current-user Unix socket.
- Telemetry: no telemetry/analytics statements found (grep telemetry/analytics in README/docs/AGENTS: none). Docs claim "Analysis runs locally". Network behaviour: setup "never downloads" Ghidra/Java; setup may install Hopper only after explicit approval and lists network origins in its plan; JEB endpoint restricted to loopback; source-map fetch only with explicit opt-in; IDA Free cloud decompiler needs network (vendor). Executed targets (process capture, ADB, Playwright) can have external effects (DISCLAIMER "Runtime, network, and device operations").
- Prompt injection: no dedicated section. Related controls: MCP prompt arguments/completions "rendered as untrusted selection data, not instructions or authorization" (docs/mcp-prompts.md); WebMCP schemas "untrusted JSON data"; skill reference android-applications.md says decompiled text is a static observation, not execution; Evidence model separates observation/inference/unknown. No filtering/sanitising of decompiled strings is documented.

## 6. Versus our test findings
(a) CONFIRMED and documented as BYO env: REA_JADX_MCP_JAR (+JAVA_HOME) is "set in the shell or MCP server environment" (docs/android-analysis.md L17-22); Ghidra uses GHIDRA_INSTALL_DIR/JAVA_HOME. `rea setup` (src/application/SetupPlan.ts L308-323) writes only "detected provider environment" (Ghidra/Hopper/Java paths it finds) and "retains existing server environment overrides"; nothing in the code/docs shows setup detecting REA_JADX_MCP_JAR, REA_APKTOOL_COMMAND, etc. Documented fix: add the variables manually to the `env` object of the `mcpServers.rea` entry in the client config (the same pattern docs/client-configuration.md L23/L53 give for REA_MCP_INPUT_SCHEMA_PROFILE; docs/windows-ghidra-p0.md shows a full `env` block with REA_ANALYSIS_PROVIDER, GHIDRA_INSTALL_DIR, JAVA_HOME), then restart the client; setup keeps them on re-run. No dedicated "JADX via MCP" how-to; this is inferred from these docs. Use `rea doctor --provider ghidra --json` / `rea inspect-android-package` to verify. Also set REA_ANALYSIS_PROVIDER=ghidra if Hopper is also present (installation.md ~L580).
(b) CONFIRMED: Android needs jadx-headless-mcp 0.7.1 (third-party, pinned git submodule third_party; REA does not install it) + full JDK 17+. Windows arm64 unsupported; Linux bridge on JDK 25 unverified.
(c) CONFIRMED: Ghidra must be 12.1.x (accepts 12.1.*, verified 12.1.4); JDK 21+; doctor rejects other versions. On macOS x64 the native decompiler may need a manual build (installation.md ~L590).
