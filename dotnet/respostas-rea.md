# REA evaluation: LibreHardwareMonitor 0.9.6.0 (.NET Framework 4.7.2, x64, IL-only, unsigned, unobfuscated)

Mode tags: [M1] = REA only, [M2] = ilspycmd 9.1 decompiled text (the REA import workflow adds only hash-binding, see verdict).

## a. Architecture (confidence: high for roles and types, medium for the deep internals)
- LibreHardwareMonitor.exe: WinForms GUI [M1: `inspect-managed-artifact` references System.Windows.Forms, Aga.Controls (TreeViewAdv), OxyPlot.WindowsForms, Microsoft.Win32.TaskScheduler, System.Web, System.Text.Json]. Entry point token 0x06000003 = `LibreHardwareMonitor.Program.Main` (STAThread; Application.Run, new `UI.MainForm`) [M1 entry token and CIL anchors; M2 body]. `Program.AllRequiredFilesAvailable` checks that the sibling DLLs exist. Other types [M1 members]: UI.MainForm, SensorNode/HardwareNode/TypeNode/TreeModel, SensorGadget/Gadget, SystemTray/SensorNotifyIcon, PlotPanel, Themes.Light/Dark/BlackTheme, StartupManager, AuthForm, InterfacePortForm, ParameterForm, Utilities.HttpServer/PersistentSettings/Logger/IconFactory.
- LibreHardwareMonitorLib.dll: the engine (653 TypeDefs, 2575 methods, 8725 fields) [M1 metadata counts]. Embeds PawnIo modules as resources. Core abstractions [M2 only; see limits]: `Computer : IComputer` with `IsCpuEnabled/IsGpuEnabled/IsMotherboardEnabled/IsNetworkEnabled/IsStorageEnabled/...`, `Hardware : IHardware`, `Sensor : ISensor`, enums `HardwareType` (Motherboard, SuperIO, Cpu, Memory, GpuNvidia/Amd/Intel, Storage, Network, Cooler, EmbeddedController, Psu, Battery, PowerMonitor) and `SensorType` (Voltage..Humidity). Hardware classes: GenericCpu, IntelCpu, SuperIOHardware, LpcIO, CpuId, Mutexes.
- Third-party [M1 AssemblyRefs/files]: HidSharp, DiskInfoToolkit, RAMSPDToolkit-NDD, BlackSharp.Core, OxyPlot, Aga.Controls, TaskScheduler, System.Text.Json, plus BCL polyfills. Web UI embeds jQuery 1.7.2, jQuery UI, knockout 2.1 [M1 resources].

## b. Intel CPU temperature (confidence: high on mechanism, medium on exact decode details)
- Mechanism: MSR reads through the PawnIO kernel driver, not WinRing0. [M1] Lib resource `LibreHardwareMonitor.Resources.PawnIo.IntelMSR.bin` (4068 bytes) exists; exe embeds `PawnIO_setup.exe` (3.2 MB). [M1] The Lib imports `CreateFileW`, `DeviceIoControl`, `SetThreadGroupAffinity`.
- [M2] `PawnIo.LoadModuleFromResource` opens `\\?\GLOBALROOT\Device\PawnIO`, sends IOCTL 2712805508 (LoadBinary) with the embedded .bin (a PawnIO script module), then `Execute(name, long[] in, n)` sends IOCTL 2712805636 with a 32-byte ASCII function name header. `IntelMsr.ReadMsr` calls function `ioctl_read_msr`.
- [M2] `IntelCpu` reads IA32_TEMPERATURE_TARGET (0x1A2, TjMax, with a per-microarchitecture table and fallback), per-core IA32_THERM_STATUS (0x19C, digital readout; Temp = TjMax - TSlope*value), and IA32_PACKAGE_THERM_STATUS (0x1B1) for "CPU Package"; also "Core Max/Average", "Distance to TjMax"; RAPL MSRs (0x606, 0x611 etc.) for power. It pins the thread via GroupAffinity before each read.
- Driver loading: the driver is installed separately. At startup `MainForm` checks the registry `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\PawnIO` DisplayVersion; if absent or < 2.0.0.0 it prompts, extracts `PawnIO_setup.exe` to the current directory and runs it with `-install` [M2]. Requires admin. The exe's manifest resource `app.manifest` exists [M1] (contents not inspected, likely requireAdministrator, unverified).
- REA could not: show Lib method bodies (see limits), or analyze the PawnIO .bin / setup exe contents.

## c. Network (confidence: high; all [M2] from `HttpServer`, method names/entries confirmed [M1])
- Built-in `System.Net.HttpListener` server (start/stop via MainForm menu; default-on or off not verified). Default port 8085 (`settings.GetValue("listenerPort", 8085)`), prefix `http://<listenerIp or +>:<port>/`; falls back to `+` (all interfaces) if the configured IP is not local. Default listenerIp setting is "?" so it binds to all interfaces.
- Auth: optional HTTP Basic (realm "Libre Hardware Monitor"; `AuthenticationSchemes.Basic` when enabled, else Anonymous). Username compared plainly; password compared as SHA256 hash. Settings keys `authenticationEnabled/UserName/Password`. Observation: `Password` getter returns the stored hash while the constructor setter hashes its input, so a persisted hash appears to get re-hashed on load (possible bug; low confidence, not verified at runtime).
- Endpoints (GET): `/data.json` (sensor tree JSON), `/metrics` (Prometheus text), `/Sensor?action=Get|Set|ResetMinMax&id=<sensor identifier>[&value=]` (Set writes control sensors, value `null` resets to default), `/ResetAllMinMax`, `/images_icon/<name>`, any other path serves embedded `Web.*` resources (index.html, js, css). POST `/Sensor` with same query args returns `{"result":"ok"|"fail"}`. Responses add `Access-Control-Allow-Origin: *`. Unauthenticated mode + wildcard CORS + fan-control Set is a notable security concern.

## d. Settings persistence (confidence: high)
- [M2] `PersistentSettings` loads/saves an XML `<configuration><appSettings><add key=".." value=".."/>` file at `Path.ChangeExtension(Application.ExecutablePath, ".config")`, i.e. `LibreHardwareMonitor.config` next to the exe (the file `LibreHardwareMonitor.exe.config` also ships, 544 bytes, but that's a runtime config). Backup file `<name>.backup` is tried when load fails. Keys seen: listenerIp, listenerPort, authentication*, mainForm.Location.X/..., logger.fileRotation, plus per-sensor/parameter keys. Saved from a MainForm method (SaveConfiguration-like; trigger not verified). Startup autostart uses `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value `LibreHardwareMonitor` (and Microsoft.Win32.TaskScheduler referenced; not traced). [M1] confirms `PersistentSettings.Load/Save/GetValue/SetValue` members only.

## REA limits / what it could not show
- `inspect-managed-members` on LibreHardwareMonitorLib.dll returned zero types/methods: `resource-limit: Managed metadata exceeds the 67108864 byte representation budget` (coverage unavailable). So the central DLL had no member list, CIL anchors, or import workflow in Mode 1. Exe worked (111 types, 911 methods with CIL anchors, token, IL hashes).
- No string literal (#US) listing, no ports/paths/keys, no method behavior without a decompiler; REA gives member names, tokens, call-edge anchors only. Exe call_edges existed but I did not exploit them.
- Mode 1 alone: architecture and native boundaries solid; b, c, d are only guessable from names (e.g. IntelMsr.bin resource, HttpServer members), not provable.

## Stats and usability
- REA CLI calls: about 17 (2 managed-artifact, 2 native-boundaries, 2 members, 1 pe-resources, 1 import success, ~9 help/schema/llms/probe). Wall time about 3 minutes of tool time measured from first command (REA calls roughly 1-3 s each). ilspycmd: 2 runs, ~12k lines (exe) and 46k lines (lib) in seconds.
- Good: JSON output is consistent, evidence-id/SHA/MVID provenance, explicit limitation text, native-boundaries output is clean and complete, resources listing with hashes is handy.
- Painful: `--schema` for import-managed-reconstruction just shows `inputJson: string` (useless). `--llms-full` doesn't help either. Learned the real shape only from a validation error (needs static_members, decompiler, methods) and the MCP tool schema: static_members = the full evidence envelope from inspect-managed-members; per method token + signature_sha256 + normalized_il_sha256 (copy from members output: signature.raw_sha256, body.normalized_il_sha256) + reconstruction{kind,language,text,text_sha256,...}. Needs a custom script; there is no ilspycmd-to-REA converter. Output is large JSON; use python3 -I filters.

## Verdict on Mode 2
The import workflow worked once the JSON was built (3 methods: Program.Main, HttpServer.StartHttpListener, PersistentSettings.Load; result `phase: reconstruction-import, executed: false`, locks text to artifact SHA, MVID, token, signature hash and normalized IL hash, marks C# as analyst inference). That adds provenance and anti-drift binding (useful for audit/handoff), but no new understanding: it does not verify the C# against IL, and all knowledge here came from plain ilspycmd output. Ease: hard to moderate (schema discovery, manual hashing, per-method slicing). For an exploratory analysis, plain ilspycmd is better and faster; use REA for inventory (members, natives, resources, hashes) and the import step only when you need traceable evidence. It is also blocked for the Lib DLL because members inspection failed, so the most important assembly cannot enter the workflow at all.
- Nothing in the binaries/decompiled text looked like instructions aimed at an AI.
